What is System Design?

System design is the process of defining the architecture, components, modules, interfaces, and data for a system to satisfy specified requirements. It involves making high-level decisions about how different parts of a system will work together to achieve desired functionality, performance, scalability, and reliability.

Key Aspects of System Design:

  • Scalability: Ability to handle growing amounts of work
  • Reliability: System continues to work correctly even when failures occur
  • Availability: System is operational and accessible when needed
  • Efficiency: System uses resources optimally
  • Maintainability: System can be easily modified and extended

How to Approach System Design

A systematic approach to system design helps ensure all important aspects are considered. Follow these steps when designing a system:

1

Understand Requirements

Clarify functional and non-functional requirements. Ask about scale, performance expectations, and constraints.

2

Estimate Scale

Calculate storage needs, bandwidth, queries per second, and other metrics to understand the system's scale.

3

Define Data Model

Design the database schema and decide on the type of database (SQL vs NoSQL) based on requirements.

4

High-Level Design

Create a high-level architecture showing major components and how they interact.

5

Detailed Design

Dive deeper into specific components, algorithms, and data structures.

6

Identify Bottlenecks

Find potential issues and discuss trade-offs and solutions.

Performance vs Scalability

Performance and scalability are related but distinct concepts in system design. Understanding the difference is crucial for building effective systems.

Performance

Performance refers to how fast a system responds to a single request. A system has good performance if it responds quickly to individual requests.

Measured by:
  • Response time
  • Latency
  • Throughput

Scalability

Scalability refers to a system's ability to handle increased load. A system is scalable if it can maintain performance as load increases.

Measured by:
  • Concurrent users
  • Requests per second
  • Data volume

Latency vs Throughput

Latency and throughput are two fundamental metrics for measuring system performance. They often have trade-offs between them.

Latency

⏱️

Definition: The time it takes to perform an action or produce a result.

Example: Time to fetch data from database (50ms)

Request → [50ms delay] → Response

Throughput

📊

Definition: The number of operations performed per unit of time.

Example: Number of requests processed per second (1000 req/s)

1000 requests / second

The Trade-off

Generally, you can achieve high throughput with low latency, but there are trade-offs:

  • Batching requests increases throughput but may increase latency
  • Processing requests individually minimizes latency but may reduce throughput
  • The optimal balance depends on your specific use case

More requests processed overall

Availability vs Consistency

In distributed systems, there's often a trade-off between availability and consistency. Understanding this trade-off is essential for making informed design decisions.

Availability

Every request receives a response, without guarantee that it contains the most recent data.

Example: Social media feed showing slightly outdated posts to ensure the app remains responsive.

Consistency

Every read receives the most recent write or an error.

Example: Banking system ensuring account balance is always accurate, even if it means slower responses.

The Spectrum

High Availability
Eventual Consistency
Social Media, Caching
Strong Consistency
Lower Availability
Banking, Transactions

CAP Theorem

The CAP theorem states that a distributed system can only guarantee two out of three properties: Consistency, Availability, and Partition Tolerance.

Understanding the Trade-offs

CP (Consistency + Partition Tolerance)

System ensures consistency even during network partitions, but may become unavailable.

Examples: MongoDB, HBase, Redis

AP (Availability + Partition Tolerance)

System remains available during network partitions, but may return stale data.

Examples: Cassandra, DynamoDB, CouchDB

CA (Consistency + Availability)

System is consistent and available, but cannot handle network partitions.

Examples: Traditional RDBMS (single node)

Weak Consistency

After a write, reads may or may not see it. A best-effort approach is taken. This is commonly seen in systems like memcached and VoIP.

How Weak Consistency Works

T0
Write: X = 10
T1
Read: X = ? (may be 10 or old value)
T2
Read: X = ? (may be 10 or old value)

Use Cases

  • Real-time Communication: VoIP, video chat (dropped frames acceptable)
  • Caching: Memcached (stale data acceptable for performance)
  • Gaming: Multiplayer games (slight inconsistencies acceptable)

Eventual Consistency

After a write, reads will eventually see it (typically within milliseconds). Data is replicated asynchronously. This is commonly used in DNS and email systems.

How Eventual Consistency Works

Primary
X = 10
Write happens here
→
→
Async replication
Replica 1
X = 5 → 10
Replica 2
X = 5 → 10

Characteristics

  • High availability and performance
  • Works well in distributed systems
  • Temporary inconsistencies are acceptable
  • Eventually all replicas converge to the same value

Use Cases

  • DNS: Domain name updates propagate gradually
  • Social Media: Likes, comments may take time to appear everywhere
  • E-commerce: Product inventory counts (approximate is acceptable)

Strong Consistency

After a write, reads will always see it. Data is replicated synchronously. This is used in file systems and RDBMSes where consistency is critical.

How Strong Consistency Works

1. Write Request
Primary: X = 10
↓ Synchronous replication
2. Wait for Acknowledgment
Replica 1: X = 10 ✓
Replica 2: X = 10 ✓
↓ All replicas updated
3. Confirm Write
Write confirmed - All reads will see X = 10

Characteristics

  • Guaranteed consistency across all nodes
  • Higher latency due to synchronous replication
  • May sacrifice availability during network issues
  • Simpler to reason about for developers

Use Cases

  • Banking: Account balances must be accurate
  • Inventory Management: Stock levels must be precise
  • Booking Systems: Prevent double-booking

Key Insights

  • 99.9% (Three nines) is acceptable for most web applications
  • 99.99% (Four nines) is the target for critical business applications
  • 99.999% (Five nines) is extremely difficult and expensive to achieve
  • Each additional nine requires exponentially more effort and cost

DNS Considerations

  • Caching: DNS responses are cached at multiple levels to improve performance
  • TTL (Time To Live): Determines how long DNS records are cached
  • DNS Propagation: Changes can take time to propagate globally (up to 48 hours)
  • Load Balancing: DNS can return different IPs for load distribution
  • Failover: DNS can route traffic away from failed servers

CDN Delivery Methods

Push CDNs

Content is uploaded to CDN servers when it changes. You're responsible for providing content and updating it.

Best for: Sites with small traffic, content that doesn't change often

Pull CDNs

CDN grabs content from your server when a user requests it for the first time. Content is cached on CDN until TTL expires.

Best for: Sites with heavy traffic, frequently changing content

Load Balancing Algorithms

Different algorithms determine how load balancers distribute traffic across servers. The choice depends on your specific requirements and traffic patterns.

Round Robin

Req 1 → Server 1
Req 2 → Server 2
Req 3 → Server 3
Req 4 → Server 1

Distributes requests sequentially across all servers in rotation.

Best for: Servers with similar capabilities
Pros: Simple, fair distribution
Cons: Doesn't consider server load or capacity

Least Connections

S1: 5 connections
S2: 2 connections ← New request
S3: 7 connections

Routes traffic to the server with the fewest active connections.

Best for: Long-lived connections
Pros: Balances load dynamically
Cons: More complex to implement

Weighted Round Robin

S1 (weight: 3): 60% traffic
S2 (weight: 2): 40% traffic

Assigns weights to servers based on their capacity, distributing more traffic to higher-capacity servers.

Best for: Servers with different capacities
Pros: Accounts for server capabilities
Cons: Requires manual weight configuration

IP Hash

IP: 192.168.1.1 → hash → Server 2
IP: 192.168.1.2 → hash → Server 1
IP: 192.168.1.1 → hash → Server 2

Uses client IP address to determine which server receives the request. Same client always goes to same server.

Best for: Session persistence requirements
Pros: Maintains session affinity
Cons: Uneven distribution if IPs not diverse

Least Response Time

S1: 150ms
S2: 50ms ← New request
S3: 200ms

Routes to the server with the fastest response time and fewest active connections.

Best for: Performance-critical applications
Pros: Optimizes for speed
Cons: Requires response time monitoring

Random

Req 1 → Server 2
Req 2 → Server 1
Req 3 → Server 2
Req 4 → Server 3

Randomly selects a server for each request.

Best for: Simple setups with similar servers
Pros: Very simple, no state needed
Cons: May not distribute evenly in short term

Layer 4 vs Layer 7 Load Balancing

Load balancers can operate at different layers of the OSI model, each with its own advantages and use cases.

Layer 4 (Transport Layer)

Operates at the transport layer, making routing decisions based on IP address and TCP/UDP port.

How it works:

  • Examines packet headers (source/destination IP and port)
  • Makes routing decisions without inspecting packet content
  • Maintains connection state
  • Faster because it doesn't need to decrypt or inspect content
Advantages:
  • Faster performance
  • Lower latency
  • Can handle any protocol
  • More secure (doesn't decrypt traffic)
Disadvantages:
  • Limited routing intelligence
  • Cannot make content-based decisions
  • No application-level features
Use cases: High-performance scenarios, non-HTTP protocols, when you don't need content inspection

Layer 7 (Application Layer)

Operates at the application layer, making routing decisions based on content of the request (URLs, headers, cookies, etc.).

How it works:

  • Inspects HTTP headers, URLs, and content
  • Can route based on application-specific data
  • Can modify requests and responses
  • Terminates and re-establishes connections
Advantages:
  • Intelligent routing (URL-based, header-based)
  • Can perform SSL termination
  • Content caching
  • Request/response modification
Disadvantages:
  • Higher latency
  • More resource intensive
  • HTTP/HTTPS specific
Use cases: Microservices routing, A/B testing, content-based routing, SSL termination

When to Use Each Approach

Choose Horizontal Scaling When:

  • You need to handle massive scale
  • High availability is critical
  • You want to use cloud infrastructure
  • Your application is stateless or can be made stateless

Choose Vertical Scaling When:

  • Your application can't be distributed easily
  • You need strong consistency
  • Initial scale is sufficient
  • Simpler operations are preferred
