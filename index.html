What is System Design?

System design is the process of defining the architecture, components, modules, interfaces, and data for a system to satisfy specified requirements. It involves making high-level decisions about how different parts of a system will work together to achieve desired functionality, performance, scalability, and reliability.

Key Aspects of System Design:

  • Scalability: Ability to handle growing amounts of work
  • Reliability: System continues to work correctly even when failures occur
  • Availability: System is operational and accessible when needed
  • Efficiency: System uses resources optimally
  • Maintainability: System can be easily modified and extended

How to Approach System Design

A systematic approach to system design helps ensure all important aspects are considered. Follow these steps when designing a system:

1

Understand Requirements

Clarify functional and non-functional requirements. Ask about scale, performance expectations, and constraints.

2

Estimate Scale

Calculate storage needs, bandwidth, queries per second, and other metrics to understand the system's scale.

3

Define Data Model

Design the database schema and decide on the type of database (SQL vs NoSQL) based on requirements.

4

High-Level Design

Create a high-level architecture showing major components and how they interact.

5

Detailed Design

Dive deeper into specific components, algorithms, and data structures.

6

Identify Bottlenecks

Find potential issues and discuss trade-offs and solutions.

Performance vs Scalability

Performance and scalability are related but distinct concepts in system design. Understanding the difference is crucial for building effective systems.

Performance

Performance refers to how fast a system responds to a single request. A system has good performance if it responds quickly to individual requests.

Measured by:
  • Response time
  • Latency
  • Throughput

Scalability

Scalability refers to a system's ability to handle increased load. A system is scalable if it can maintain performance as load increases.

Measured by:
  • Concurrent users
  • Requests per second
  • Data volume

Latency vs Throughput

Latency and throughput are two fundamental metrics for measuring system performance. They often have trade-offs between them.

Latency

⏱️

Definition: The time it takes to perform an action or produce a result.

Example: Time to fetch data from database (50ms)

Request → [50ms delay] → Response

Throughput

📊

Definition: The number of operations performed per unit of time.

Example: Number of requests processed per second (1000 req/s)

1000 requests / second

The Trade-off

Generally, you can achieve high throughput with low latency, but there are trade-offs:

  • Batching requests increases throughput but may increase latency
  • Processing requests individually minimizes latency but may reduce throughput
  • The optimal balance depends on your specific use case

Availability vs Consistency

In distributed systems, there's often a trade-off between availability and consistency. Understanding this trade-off is essential for making informed design decisions.

Availability

Every request receives a response, without guarantee that it contains the most recent data.

Example: Social media feed showing slightly outdated posts to ensure the app remains responsive.

Consistency

Every read receives the most recent write or an error.

Example: Banking system ensuring account balance is always accurate, even if it means slower responses.

The Spectrum

High Availability
Eventual Consistency
Social Media, Caching
Strong Consistency
Lower Availability
Banking, Transactions

CAP Theorem

The CAP theorem states that a distributed system can only guarantee two out of three properties: Consistency, Availability, and Partition Tolerance.

Understanding the Trade-offs

CP (Consistency + Partition Tolerance)

System ensures consistency even during network partitions, but may become unavailable.

Examples: MongoDB, HBase, Redis

AP (Availability + Partition Tolerance)

System remains available during network partitions, but may return stale data.

Examples: Cassandra, DynamoDB, CouchDB

CA (Consistency + Availability)

System is consistent and available, but cannot handle network partitions.

Examples: Traditional RDBMS (single node)

Weak Consistency

After a write, reads may or may not see it. A best-effort approach is taken. This is commonly seen in systems like memcached and VoIP.

How Weak Consistency Works

T0
Write: X = 10
T1
Read: X = ? (may be 10 or old value)
T2
Read: X = ? (may be 10 or old value)

Use Cases

  • Real-time Communication: VoIP, video chat (dropped frames acceptable)
  • Caching: Memcached (stale data acceptable for performance)
  • Gaming: Multiplayer games (slight inconsistencies acceptable)

Eventual Consistency

After a write, reads will eventually see it (typically within milliseconds). Data is replicated asynchronously. This is commonly used in DNS and email systems.

How Eventual Consistency Works

Primary
X = 10
Write happens here
→
→
Async replication
Replica 1
X = 5 → 10
Replica 2
X = 5 → 10

Characteristics

  • High availability and performance
  • Works well in distributed systems
  • Temporary inconsistencies are acceptable
  • Eventually all replicas converge to the same value

Use Cases

  • DNS: Domain name updates propagate gradually
  • Social Media: Likes, comments may take time to appear everywhere
  • E-commerce: Product inventory counts (approximate is acceptable)

Strong Consistency

After a write, reads will always see it. Data is replicated synchronously. This is used in file systems and RDBMSes where consistency is critical.

How Strong Consistency Works

1. Write Request
Primary: X = 10
↓ Synchronous replication
2. Wait for Acknowledgment
Replica 1: X = 10 ✓
Replica 2: X = 10 ✓
↓ All replicas updated
3. Confirm Write
Write confirmed - All reads will see X = 10

Characteristics

  • Guaranteed consistency across all nodes
  • Higher latency due to synchronous replication
  • May sacrifice availability during network issues
  • Simpler to reason about for developers

Use Cases

  • Banking: Account balances must be accurate
  • Inventory Management: Stock levels must be precise
  • Booking Systems: Prevent double-booking

DNS Considerations

  • Caching: DNS responses are cached at multiple levels to improve performance
  • TTL (Time To Live): Determines how long DNS records are cached
  • DNS Propagation: Changes can take time to propagate globally (up to 48 hours)
  • Load Balancing: DNS can return different IPs for load distribution
  • Failover: DNS can route traffic away from failed servers

Load Balancing Algorithms

Different algorithms determine how load balancers distribute traffic across servers. The choice depends on your specific requirements and traffic patterns.

Round Robin

Req 1 → Server 1
Req 2 → Server 2
Req 3 → Server 3
Req 4 → Server 1

Distributes requests sequentially across all servers in rotation.

Best for: Servers with similar capabilities
Pros: Simple, fair distribution
Cons: Doesn't consider server load or capacity

Least Connections

S1: 5 connections
S2: 2 connections ← New request
S3: 7 connections

Routes traffic to the server with the fewest active connections.

Best for: Long-lived connections
Pros: Balances load dynamically
Cons: More complex to implement

Weighted Round Robin

S1 (weight: 3): 60% traffic
S2 (weight: 2): 40% traffic

Assigns weights to servers based on their capacity, distributing more traffic to higher-capacity servers.

Best for: Servers with different capacities
Pros: Accounts for server capabilities
Cons: Requires manual weight configuration

IP Hash

IP: 192.168.1.1 → hash → Server 2
IP: 192.168.1.2 → hash → Server 1
IP: 192.168.1.1 → hash → Server 2

Uses client IP address to determine which server receives the request. Same client always goes to same server.

Best for: Session persistence requirements
Pros: Maintains session affinity
Cons: Uneven distribution if IPs not diverse

Least Response Time

S1: 150ms
S2: 50ms ← New request
S3: 200ms

Routes to the server with the fastest response time and fewest active connections.

Best for: Performance-critical applications
Pros: Optimizes for speed
Cons: Requires response time monitoring

Random

Req 1 → Server 2
Req 2 → Server 1
Req 3 → Server 2
Req 4 → Server 3

Randomly selects a server for each request.

Best for: Simple setups with similar servers
Pros: Very simple, no state needed
Cons: May not distribute evenly in short term

Layer 4 vs Layer 7 Load Balancing

Load balancers can operate at different layers of the OSI model, each with its own advantages and use cases.

Layer 4 (Transport Layer)

Operates at the transport layer, making routing decisions based on IP address and TCP/UDP port.

How it works:

  • Examines packet headers (source/destination IP and port)
  • Makes routing decisions without inspecting packet content
  • Maintains connection state
  • Faster because it doesn't need to decrypt or inspect content
Advantages:
  • Faster performance
  • Lower latency
  • Can handle any protocol
  • More secure (doesn't decrypt traffic)
Disadvantages:
  • Limited routing intelligence
  • Cannot make content-based decisions
  • No application-level features
Use cases: High-performance scenarios, non-HTTP protocols, when you don't need content inspection

Layer 7 (Application Layer)

Operates at the application layer, making routing decisions based on content of the request (URLs, headers, cookies, etc.).

How it works:

  • Inspects HTTP headers, URLs, and content
  • Can route based on application-specific data
  • Can modify requests and responses
  • Terminates and re-establishes connections
Advantages:
  • Intelligent routing (URL-based, header-based)
  • Can perform SSL termination
  • Content caching
  • Request/response modification
Disadvantages:
  • Higher latency
  • More resource intensive
  • HTTP/HTTPS specific
Use cases: Microservices routing, A/B testing, content-based routing, SSL termination

When to Use Each Approach

Choose Horizontal Scaling When:

  • You need to handle massive scale
  • High availability is critical
  • You want to use cloud infrastructure
  • Your application is stateless or can be made stateless

Choose Vertical Scaling When:

  • Your application can't be distributed easily
  • You need strong consistency
  • Initial scale is sufficient
  • Simpler operations are preferred

Data Architecture Patterns

Lambda Architecture

Layers:

  • Batch Layer → Historical Data Processing
  • Speed Layer → Real-time Processing
  • Serving Layer → Query Results

Use Case: When you need both batch and real-time processing with eventual consistency.

Pros: Handles both batch and real-time, fault-tolerant

Cons: Complex to maintain, duplicate logic

Kappa Architecture

Layers:

  • Stream Processing Layer → All Data as Streams
  • Serving Layer → Query Results

Use Case: When all data can be treated as streams.

Pros: Simpler than Lambda, single codebase

Cons: Requires reprocessing for historical data

Data Mesh

Principles:

  • Domain-Oriented Data Ownership
  • Data as a Product
  • Self-Serve Data Infrastructure
  • Federated Computational Governance

Use Case: Large organizations with multiple data domains.

Pros: Scalable, domain ownership, decentralized

Cons: Requires organizational change, complex governance

SQL vs NoSQL

Choosing between SQL and NoSQL databases depends on your specific requirements for data structure, scalability, consistency, and query patterns.

SQL (Relational Databases)

Characteristics:

  • Structured data with predefined schema
  • ACID transactions (Atomicity, Consistency, Isolation, Durability)
  • Relationships via foreign keys
  • Powerful query language (SQL)
  • Vertical scaling primarily

Best For:

  • Complex queries and joins
  • Transactions requiring ACID guarantees
  • Structured data with clear relationships
  • Financial systems, e-commerce

Examples:

PostgreSQL, MySQL, Oracle, SQL Server

NoSQL (Non-Relational Databases)

Characteristics:

  • Flexible schema or schema-less
  • BASE properties (Basically Available, Soft state, Eventual consistency)
  • Horizontal scaling
  • Optimized for specific data models
  • High performance for specific use cases

Best For:

  • Massive scale and high throughput
  • Flexible or evolving data models
  • Hierarchical or unstructured data
  • Real-time applications, IoT, social media

Types:

Key-Value, Document, Column-Family, Graph

Database Replication

Database replication involves copying and maintaining database objects in multiple database servers for redundancy, availability, and performance.

Master-Slave Replication

One master handles writes, multiple slaves handle reads

Master (Write) → Replication → Slave 1 (Read)
Master (Write) → Replication → Slave 2 (Read)
Master (Write) → Replication → Slave 3 (Read)

Pros: Scales reads, simple to implement

Cons: Single point of failure (master), replication lag

Master-Master Replication

Multiple masters can handle both reads and writes

Master 1 (Read/Write) ↔ Master 2 (Read/Write)

Pros: No single point of failure, scales both reads and writes

Cons: Complex conflict resolution, consistency challenges

Database Sharding

Sharding is a database partitioning technique that splits data across multiple database instances (shards) to improve scalability and performance.

Sharding Strategies

Hash-Based Sharding

Use a hash function on a key to determine which shard stores the data

Example: user_id % num_shards

Pros: Even distribution

Cons: Difficult to add/remove shards

Range-Based Sharding

Partition data based on ranges of a key

Example: A-M → Shard 1, N-Z → Shard 2

Pros: Simple, good for range queries

Cons: Can lead to hotspots

Directory-Based Sharding

Maintain a lookup table that maps keys to shards

Pros: Flexible, easy to add shards

Cons: Lookup table is a single point of failure

Challenges

  • Joins across shards are expensive
  • Rebalancing data when adding/removing shards
  • Maintaining referential integrity
  • Increased complexity in application logic

Database Federation

Federation (functional partitioning) splits databases by function, with each database serving a specific domain or feature.

Example Architecture

Users DB → User profiles, authentication
Products DB → Product catalog, inventory
Orders DB → Order history, transactions
Analytics DB → Reporting, metrics

Benefits

  • Reduces read/write traffic to each database
  • Smaller databases are faster to query
  • Can use different database technologies per function
  • Easier to scale specific functions independently

Drawbacks

  • Joins across databases require application-level logic
  • Increased complexity in maintaining multiple databases
  • Transactions spanning multiple databases are difficult

Denormalization

Denormalization is the process of adding redundant data to improve read performance by reducing the need for expensive joins.

Normalized (3NF)

Data is organized to minimize redundancy

Users Table: user_id, name

Orders Table: order_id, user_id, product_id

Products Table: product_id, name, price

Pros: No data redundancy, easier updates

Cons: Requires joins, slower reads

Denormalized

Redundant data is added for faster reads

Orders Table: order_id, user_id, user_name, product_id, product_name, product_price

Pros: Faster reads, no joins needed

Cons: Data redundancy, complex updates

When to Denormalize

  • Read-heavy workloads where performance is critical
  • Data that rarely changes
  • When joins are becoming a bottleneck
  • Reporting and analytics queries

SQL Tuning

SQL tuning involves optimizing database queries and schema design to improve performance.

Key Optimization Techniques

1. Indexing

  • Create indexes on frequently queried columns
  • Use composite indexes for multi-column queries
  • Avoid over-indexing (slows writes)
  • Use covering indexes to avoid table lookups

2. Query Optimization

  • Use EXPLAIN to analyze query execution plans
  • Avoid SELECT * - specify needed columns
  • Use WHERE clauses to filter early
  • Avoid functions on indexed columns in WHERE
  • Use LIMIT to restrict result sets

3. Join Optimization

  • Join on indexed columns
  • Use appropriate join types (INNER, LEFT, etc.)
  • Consider denormalization for complex joins
  • Use subqueries judiciously

4. Schema Design

  • Choose appropriate data types
  • Normalize to reduce redundancy
  • Denormalize for read performance
  • Partition large tables

Characteristics

  • Simple data model: key → value
  • Horizontal scalability

Use Cases

Document Store

Document stores manage semi-structured data as documents (typically JSON, BSON, or XML).

Characteristics

  • Flexible schema - each document can have different fields
  • Documents can be nested and contain arrays
  • Query by any field in the document

Use Cases

  • User profiles with varying attributes

Examples

Couchbase: High performance, mobile sync

Wide Column Store

Wide column stores organize data in columns rather than rows, optimized for queries over large datasets.

Characteristics

  • Data stored in column families
  • Each row can have different columns
  • Optimized for write-heavy workloads

Use Cases

  • Time-series data (IoT sensors, logs)

  • Analytics on large datasets

Examples

Cassandra: Highly scalable, no single point of failure

HBase: Built on Hadoop, good for real-time reads/writes

Graph Database

Graph databases store data as nodes and relationships, optimized for traversing connections.

Characteristics

  • Nodes represent entities
  • Edges represent relationships
  • Properties on both nodes and edges

Use Cases

Caching

Caching stores frequently accessed data in fast storage to reduce latency and database load.

Cache Levels

Client Caching → Browser cache, mobile app cache
CDN Caching → Static content at edge locations
Web Server Caching → Reverse proxy cache (Varnish, Nginx)
Application Caching → In-memory cache (Redis, Memcached)
Database Caching → Query result cache, buffer pool

Benefits

  • Reduced latency - faster response times
  • Reduced database load
  • Improved scalability
  • Cost savings on database resources

Cache Strategies

Different caching strategies determine how data is loaded into and updated in the cache.

Cache-Aside (Lazy Loading)

Application checks cache first, loads from DB on miss

1. App checks cache
2. Cache miss → Read from DB
3. Write to cache
4. Return data

Pros: Only caches requested data

Cons: Cache miss penalty, stale data possible

Write-Through

Data is written to cache and database simultaneously

1. Write to cache
2. Write to DB (synchronous)
3. Confirm write

Pros: Cache always consistent with DB

Cons: Higher write latency

Write-Behind (Write-Back)

Data written to cache first, DB updated asynchronously

1. Write to cache
2. Confirm write immediately
3. Async write to DB later

Pros: Low write latency, batching possible

Cons: Risk of data loss if cache fails

Refresh-Ahead

Automatically refresh cache before expiration

1. Predict which data will be needed
2. Refresh before TTL expires
3. Always serve from cache

Pros: Reduced latency for predicted data

Cons: Can waste resources on unused data

Types of Caching

Eviction Policies

LRU (Least Recently Used)

Evicts the least recently accessed items first

Best for: General purpose caching

LFU (Least Frequently Used)

Evicts items accessed least often

Best for: Long-term access patterns

FIFO (First In First Out)

Evicts oldest items first

Best for: Simple, predictable eviction

TTL (Time To Live)

Items expire after a set time

Best for: Time-sensitive data

Cache Invalidation

Keeping cache consistent with the source of truth is one of the hardest problems in computer science.

  • TTL-based: Set expiration time for cached data
  • Event-based: Invalidate on data updates
  • Manual: Explicit cache clearing

Message Queues

Message queues enable asynchronous communication between services by storing messages until they can be processed.

How Message Queues Work

Producer → Message Queue → Consumer
Multiple Producers → Queue → Multiple Consumers

Benefits

  • Decoupling - producers and consumers are independent
  • Scalability - add more consumers to handle load
  • Reliability - messages persisted until processed
  • Load leveling - smooth out traffic spikes

Common Patterns

Work Queue

Distribute tasks among workers

Use case: Image processing, email sending

Pub/Sub

Broadcast messages to multiple subscribers

Use case: Event notifications, real-time updates

Examples

RabbitMQ: Feature-rich, supports multiple protocols

Apache Kafka: High throughput, distributed streaming

AWS SQS: Managed, simple to use

Redis Streams: Fast, in-memory

Task Queues

Task queues manage background jobs and scheduled tasks, allowing applications to offload time-consuming operations.

Use Cases

  • Sending emails asynchronously
  • Processing uploaded files
  • Generating reports
  • Scheduled maintenance tasks
  • Batch processing

Task Queue Components

Producer

Creates and enqueues tasks

Queue/Broker

Stores tasks until workers are available

Worker

Processes tasks from the queue

Result Backend

Stores task results and status

Examples

Celery: Python, distributed task queue

Back Pressure

Back pressure occurs when a system receives more requests than it can handle, requiring mechanisms to prevent overload.

Handling Back Pressure

1. Buffering

Queue requests temporarily

Risk: Buffer overflow if sustained overload

2. Dropping

Reject new requests when overloaded

Strategy: Return 503 Service Unavailable

3. Throttling

Limit request rate per client

Methods: Rate limiting, token bucket

4. Auto-scaling

Add more workers/servers dynamically

Benefit: Handles temporary spikes

Monitoring Back Pressure

  • Queue depth/length
  • Consumer lag
  • Request latency
  • Error rates

HTTP

HTTP (Hypertext Transfer Protocol) is the foundation of data communication on the web, operating at the application layer.

HTTP Methods

GET

Retrieve data, idempotent, cacheable

POST

Create resources, not idempotent

PUT

Update/replace resources, idempotent

PATCH

Partial update, idempotent

DELETE

Remove resources, idempotent

HTTP Status Codes

  • 2xx Success: 200 OK, 201 Created, 204 No Content
  • 3xx Redirection: 301 Moved Permanently, 304 Not Modified
  • 4xx Client Error: 400 Bad Request, 401 Unauthorized, 404 Not Found
  • 5xx Server Error: 500 Internal Server Error, 503 Service Unavailable

HTTP/2 and HTTP/3

HTTP/2: Multiplexing, server push, header compression

HTTP/3: Built on QUIC (UDP), faster connection establishment

TCP

TCP (Transmission Control Protocol) provides reliable, ordered, and error-checked delivery of data between applications.

Key Features

  • Connection-oriented: Three-way handshake (SYN, SYN-ACK, ACK)
  • Reliable: Acknowledgments and retransmissions
  • Ordered: Packets delivered in sequence
  • Flow control: Prevents overwhelming receiver
  • Congestion control: Adapts to network conditions

Use Cases

  • Web browsing (HTTP/HTTPS)
  • Email (SMTP, IMAP)
  • File transfer (FTP, SFTP)
  • Any application requiring reliable delivery

Trade-offs

Pros: Reliable, ordered delivery

Cons: Higher latency due to handshakes and acknowledgments

UDP

UDP (User Datagram Protocol) is a connectionless protocol that sends data without guaranteeing delivery or order.

Key Features

  • Connectionless: No handshake, just send
  • Unreliable: No acknowledgments or retransmissions
  • Unordered: Packets may arrive out of order
  • Low overhead: Minimal protocol overhead
  • Fast: Lower latency than TCP

Use Cases

  • Video streaming (some packet loss acceptable)
  • Online gaming (low latency critical)
  • VoIP (Voice over IP)
  • DNS queries
  • IoT sensors (frequent small updates)

Trade-offs

Pros: Low latency, low overhead

Cons: No reliability guarantees, application must handle packet loss

RPC (Remote Procedure Call)

RPC allows a program to execute procedures on a remote server as if they were local function calls.

How RPC Works

1. Client calls local stub
2. Stub marshals parameters
3. Network transmission
4. Server stub unmarshals parameters
5. Execute procedure
6. Return result to client

gRPC

Modern RPC framework by Google using Protocol Buffers

  • HTTP/2 based
  • Binary protocol (efficient)
  • Strongly typed contracts
  • Supports streaming
  • Multiple language support

Use Cases

  • Microservices communication
  • Internal APIs
  • Real-time services
  • Mobile-backend communication

REST (Representational State Transfer)

REST is an architectural style for designing networked applications using HTTP methods and stateless communication.

REST Principles

  • Stateless: Each request contains all necessary information
  • Client-Server: Separation of concerns
  • Cacheable: Responses can be cached
  • Uniform Interface: Consistent API design
  • Layered System: Intermediaries allowed

RESTful API Design

GET /users - List all users

GET /users/123 - Get user 123

POST /users - Create new user

PUT /users/123 - Update user 123

DELETE /users/123 - Delete user 123

Advantages

  • Simple and intuitive
  • Leverages HTTP features (caching, status codes)
  • Stateless (easy to scale)
  • Wide tooling support

GraphQL

GraphQL is a query language for APIs that allows clients to request exactly the data they need.

Key Features

  • Single endpoint: All queries to one URL
  • Client-specified queries: Request exactly what you need
  • Strongly typed schema: Self-documenting API
  • No over-fetching: Get only requested fields
  • No under-fetching: Get related data in one request

GraphQL vs REST

GraphQL

Pros: Flexible queries, single request for complex data, strong typing

Cons: More complex to implement, caching challenges, potential for expensive queries

REST

Pros: Simple, cacheable, wide support, mature tooling

Cons: Over/under-fetching, multiple endpoints, versioning challenges

Use Cases

  • Mobile apps (minimize data transfer)
  • Complex, interconnected data
  • Rapid frontend development
  • Aggregating multiple data sources

Microservices

Microservices architecture structures an application as a collection of small, independent services that communicate over networks.

Characteristics

  • Small, focused services (single responsibility)
  • Independently deployable
  • Loosely coupled
  • Organized around business capabilities
  • Owned by small teams
  • Technology diversity (polyglot)

Microservices vs Monolith

Microservices

Pros: Independent scaling, technology flexibility, fault isolation, faster deployment

Cons: Distributed system complexity, network latency, data consistency challenges, operational overhead

Monolith

Pros: Simpler to develop initially, easier debugging, single deployment, better performance (no network calls)

Cons: Tight coupling, difficult to scale, technology lock-in, slower deployment

Key Patterns

  • API Gateway: Single entry point for clients
  • Service Discovery: Services find each other dynamically
  • Circuit Breaker: Prevent cascading failures
  • Saga Pattern: Distributed transactions

Service Discovery

Service discovery enables services to find and communicate with each other without hard-coding network locations.

Client-Side Discovery

Client queries a service registry and selects an available instance

1. Service registers with registry
2. Client queries registry
3. Client calls service directly

Examples: Netflix Eureka, Consul

Server-Side Discovery

Client makes request to load balancer, which queries registry

1. Service registers with registry
2. Client calls load balancer
3. Load balancer queries registry
4. Load balancer forwards to service

Examples: Kubernetes Services, AWS ELB

Health Checks

Services periodically report health to registry

  • Heartbeat mechanism
  • Remove unhealthy instances
  • Automatic failover

Strangler Fig Pattern

Gradually migrate a legacy system by incrementally replacing specific pieces of functionality with new services.

How It Works

1. Create facade/proxy in front of legacy system
2. Implement new functionality in new service
3. Route new requests to new service
4. Gradually replace all functionality
5. Retire legacy system

Benefits

  • Incremental migration reduces risk
  • Can roll back individual pieces
  • Business continues operating during migration
  • Learn and adapt as you go

Sidecar Pattern

Deploy helper components alongside your main application to provide supporting features without modifying the application.

Common Sidecar Uses

  • Logging: Collect and forward logs
  • Monitoring: Collect metrics
  • Configuration: Dynamic config updates
  • Networking: Service mesh proxy (Envoy, Linkerd)
  • Security: Authentication, encryption

Benefits

  • Separation of concerns
  • Reusable across services
  • Language-agnostic
  • Independent deployment and scaling

Example: Service Mesh

Each service has a sidecar proxy that handles all network communication, providing features like load balancing, retries, circuit breaking, and observability.

CQRS (Command Query Responsibility Segregation)

CQRS separates read and write operations into different models, optimizing each for its specific use case.

Architecture

Command Side (Write)

Handles create, update, delete operations

Optimized for writes and business logic

Write database (normalized)

Query Side (Read)

Handles read operations

Optimized for queries and views

Read database (denormalized)

Benefits

  • Independent scaling of reads and writes
  • Optimized data models for each operation
  • Simplified queries (no complex joins)
  • Better performance

Challenges

  • Increased complexity
  • Eventual consistency between read and write models
  • Synchronization overhead

Event Sourcing

Store all changes to application state as a sequence of events, rather than just the current state.

How It Works

1. Command triggers event
2. Event stored in event store
3. Event applied to aggregate
4. State updated

Benefits

  • Complete audit trail: Every change is recorded
  • Time travel: Reconstruct state at any point in time
  • Event replay: Rebuild state or create new projections
  • Debugging: Understand how state was reached

Use Cases

  • Financial systems (transaction history)
  • Audit requirements
  • Complex business domains
  • Systems requiring temporal queries

Challenges

  • Event store can grow large
  • Eventual consistency
  • Event versioning and schema evolution
  • Query complexity

Saga Pattern

Manage distributed transactions across multiple services by breaking them into a sequence of local transactions.

Choreography-Based Saga

Each service produces and listens to events, coordinating the saga through event chains

Service A → Event → Service B → Event → Service C

Pros: Decentralized, simple for simple workflows

Cons: Hard to understand complex flows, tight coupling through events

Orchestration-Based Saga

Central orchestrator tells each service what to do

Orchestrator → Service A
Orchestrator → Service B
Orchestrator → Service C

Pros: Centralized logic, easier to understand and test

Cons: Orchestrator can become complex, single point of failure

Compensating Transactions

If a step fails, execute compensating transactions to undo previous steps

  • Order created → Cancel order
  • Payment processed → Refund payment
  • Inventory reserved → Release inventory

Circuit Breaker

Prevent cascading failures by stopping requests to a failing service and allowing it time to recover.

Circuit Breaker States

Closed (Normal)

Requests pass through normally

Count failures

Open (Failing)

Requests fail immediately

No calls to service

Wait for timeout

Half-Open (Testing)

Allow limited requests

Test if service recovered

Close if success, Open if fail

Benefits

  • Prevents resource exhaustion
  • Fails fast instead of waiting
  • Gives failing service time to recover
  • Provides fallback behavior

Bulkhead Pattern

Isolate resources for different parts of the system to prevent failures in one area from affecting others.

Implementation Strategies

Thread Pool Isolation

Separate thread pools for different services

If one service's pool is exhausted, others continue working

Connection Pool Isolation

Separate database connection pools

Prevents one service from consuming all connections

Service Instance Isolation

Deploy separate instances for critical vs non-critical workloads

Ensures critical services always have resources

Benefits

  • Fault isolation
  • Prevents resource starvation
  • Protects critical functionality
  • Easier to identify bottlenecks

Retry Pattern

Automatically retry failed operations, typically with exponential backoff and jitter.

Retry Strategies

Fixed Delay

Wait same amount between retries

Simple but can overwhelm recovering service

Exponential Backoff

Double wait time after each retry

1s, 2s, 4s, 8s, 16s...

Gives service more time to recover

Exponential Backoff + Jitter

Add randomness to backoff

Prevents thundering herd problem

Best practice for distributed systems

Best Practices

  • Set maximum retry attempts
  • Only retry transient failures (network, timeout)
  • Don't retry client errors (4xx)
  • Use idempotency to handle duplicate requests
  • Log retry attempts for monitoring

Health Monitoring

Continuously check the health and availability of services to detect and respond to failures quickly.

Health Check Types

Liveness Check

Is the service running?

Simple ping or basic endpoint

Used by orchestrators to restart failed services

Readiness Check

Is the service ready to handle requests?

Check dependencies (DB, cache, etc.)

Used by load balancers to route traffic

Deep Health Check

Comprehensive system check

Test all critical dependencies

May be expensive, run less frequently

Health Check Endpoints

GET /health/live - Liveness check

GET /health/ready - Readiness check

GET /health - Detailed health status

Response Format

  • HTTP 200 - Healthy
  • HTTP 503 - Unhealthy
  • Include details: status, dependencies, version

Monitoring

Monitoring provides visibility into system behavior, performance, and health through metrics, logs, and traces.

The Three Pillars of Observability

Metrics

Numerical measurements over time

  • CPU, memory, disk usage
  • Request rate, latency, error rate
  • Business metrics (orders, revenue)

Tools: Prometheus, Grafana, Datadog

Logs

Timestamped records of events

  • Application logs
  • Access logs
  • Error logs

Tools: ELK Stack, Splunk, Loki

Traces

Request flow through distributed system

  • Distributed tracing
  • Service dependencies
  • Performance bottlenecks

Key Metrics to Monitor

  • Latency: Response time (p50, p95, p99)
  • Traffic: Requests per second
  • Errors: Error rate, error types
  • Saturation: Resource utilization
